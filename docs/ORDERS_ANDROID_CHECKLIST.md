## Full P2 payment/recovery pass

1. **Prepare offline manual delivery.** Deny location permission. Add a manual Home address with valid Indian PIN, recipient, society/gate and delivery instructions. Select it independently of the default. Add products worth at least ₹200 within existing quantity limits, including an Rx item, then apply FIRST100 if unused. Confirm name/salt search, Home/Cart quantities and coupons still work.
2. **Review and Back.** In Cart tap Proceed to Checkout. Confirm address/recipient/instructions, available-demo/serviceability disclaimer, Rx review-required message, ASAP/evening preference, item quantities, coupon savings and exact bill. Back must retain the cart. Edit Cart and Change Address, return and verify updated details. Neither navigation nor a manual address requests GPS.
3. **Successful UPI simulation.** In a development build choose `success` under Developer simulation outcome; Continue saves the review without creating an order. On Payment tap Pay and rapidly tap again. Controls must disable while saving. Only after durable completion should Confirmation show one stable ID/count/total/address, simulated UPI success and no-money/no-fulfillment disclaimer. View Order, then Home → Orders, and verify one frozen receipt. In release, the default pending-success scenario requires Check Status before confirmation.
4. **Pending/restart.** Start a fresh eligible cart (do not reuse FIRST100). Choose `pending-success`, Continue, Pay. Check that payment says pending/unknown, order is not confirmed, cart remains intact and coupon is not newly redeemed. Force-stop/relaunch. Home/Cart must offer Resume saved payment. Check Status must resolve the original identity to one order, not create another attempt. Repeat with `pending-failure`: Check Status must fail without clearing cart/redemption.
5. **Failure/cancellation and deliberate retry.** Choose `failure` and separately `cancel`; verify no order/cart loss/redemption. Also cancel an initiated/pending payment explicitly. Review & start a new attempt must require another review, allocate new identities and keep totals correct. A successful simulation awaiting order reconciliation must not offer cancellation or imply a refund.
6. **Mock COD.** With total ≤₹2,000 choose Mock Cash on Delivery, Continue, then explicitly Confirm mock COD order. Verify one durable receipt, `COD confirmed`, and no cash collected/fulfillment claims. Totals above ₹2,000 must disable COD and explain the demo restriction.
7. **Reconciliation/crash harness.** In a controlled debug storage adapter inject failures/force-stops immediately after each of: source shopping preparation, initiated attempt, successful payment, journal intent, receipt, shopping checkpoint, journal cleanup, finalized payment marker. Include commit-with-lost-acknowledgement failures. Restart/Retry must reuse the captured identity, persist one receipt, redeem FIRST100 once and never clear a conflicting/later cart. Pending recovery must never place an order. Corrupt/unsupported records must show recovery errors without reset. A payment success plus receipt/cart failure must say reconciliation pending, not confirmed. This requires a debug harness; do not edit production persisted data casually.
8. **History and immutable receipts.** Create multiple demo orders and verify newest-first history, stable IDs/dates/counts/frozen totals, loading/empty/error/retry/missing-ID states. Edit/delete the saved address, change current selection and restart; old recipient/gate details must remain. With a controlled fixture/catalog price change, old unit prices/quantities/bill must stay unchanged. Legacy receipts without payment metadata must say it was not recorded. No real rider tracking or prescription approval appears.
9. **FIRST100 reuse.** After successful finalization, add an eligible new cart and attempt FIRST100 again. It must be rejected as already redeemed, including after restart. Failed/pending/cancelled attempts from a fresh test installation must leave it available. Do not delete the user's real app data merely to reset this test.
10. **Back, keyboard, small screens and lifecycle.** Use a small Android display and large font scale. Check safe areas/sticky CTA, scrolling, touch labels and no clipped totals. Open/close the coupon/address-form keyboard and return to Checkout without losing preference/selection. System Back from Payment must retain the saved attempt; finalized Payment must never expose Pay again. Navigate away while saving: a late callback must not pull the user back to Confirmation. Background/foreground during verification and storage, and confirm no duplicate prompt or order.
11. **Permission regressions.** Verify denied/blocked/granted foreground location, permission status Refresh without unnecessary GPS, explicit Update Location, GPS disabled and return from Settings. Saved addresses/orders must survive GPS revocation. Android Expo Go must retain notification-unavailable safeguards; custom builds must retain channel/notification permissions.

## P2 stabilization transition and presentation checks

- On a real Android build, observe Cart → Checkout → Payment and Home → Orders → Receipt: forward screens enter from the right, Back exits toward the right, and Home/Cart tabs switch without a stack slide. Check both toolbar and system Back.
- From Checkout, choose a method/evening preference, Edit Cart, then Proceed again. Verify one retained tabs entry and preserved review choices. Repeat several times; Back must not walk through duplicate Cart/Home stacks.
- Open Receipt from History, then from Confirmation; Back must return to its actual origin. Complete checkout and repeatedly Back: finalized Pay must not reappear or create another order. Continue Shopping should return to the original tabs stack.
- Turn Reduce Motion / Android animation scale off and on while using the app. Verify the preference disables transitions without remounting shopping or losing an attempt. Jest proves preference handling, not native animation appearance.
- Exercise success, pending, failed, cancelled and reconciliation states: icon, heading, explanation and actions must be distinct. Pending/reconciliation must not have a success check or claim a completed order. COD must say no cash was collected. Check TalkBack announcements and disabled/selected controls.
- Use a small display and large font scale: verify status headings, totals, product preview, saved address, itemized receipt and sticky actions wrap/read correctly. Real visual inspection remains outstanding in this implementation.
- Open/close Cart's coupon keyboard and the address form keyboard. Android should resize once without shaking or input remounting; iOS still needs its existing padding behavior. Try unsaved form Back and Back during save; verify the guard is preserved.
- Open the address form without Back history, including a missing address ID. Toolbar Back should return to one address-book entry with a returning transition. On a dirty form, Keep editing must retain the draft and Discard must complete the return. Back during save must stay blocked; a successful save should dismiss the keyboard once and return only after persistence. Also check normal book → form → Back retains the original book entry. The root tabs anchor can supply history, so verify the true no-history case with a controlled navigation fixture.
- Start a delayed payment/selection, leave the screen, refocus it before completion and trigger duplicate taps. Late callbacks from the old visit must not steal navigation. The saved intent/outcome must remain recoverable.
